# Astro 中文个人技术笔记博客

## Problem Statement

作者需要一个长期可维护、公开可访问的中文个人技术笔记博客，用于沉淀和分享技术内容。当前仓库尚未提供网站、内容模型或部署能力。作者希望写作保持接近 Markdown 的轻量体验，同时让读者获得清晰、舒适、可订阅的阅读体验，并能通过 GitHub Pages 使用 `blog.loliking.com` 访问。

## Solution

建立一个由 Astro 生成的静态中文技术博客。网站采用纸张质感的极简阅读风格，提供明暗主题、文章列表、文章详情、分类、标签、归档、RSS、关于页和可配置社交入口。文章以 Markdown 或 MDX 写作，并由统一的内容契约、发布过滤与静态构建流程保证首页、聚合页、RSS 和部署产物的一致性。

网站通过 GitHub Actions 发布到 GitHub Pages，使用 `blog.loliking.com` 作为规范域名，并在可用后强制 HTTPS。

## User Stories

1. 作为博客作者，我想用 Markdown 编写技术文章，以便快速发布和长期维护内容。
2. 作为博客作者，我想在必要时使用 MDX，以便在文章中嵌入交互组件或复杂示例。
3. 作为博客作者，我想为每篇文章填写中文标题、摘要、发布日期、稳定 slug 和分类，以便内容可以可靠展示、检索和订阅。
4. 作为博客作者，我想为文章添加可选的更新时间，以便读者知道技术笔记是否仍然新鲜。
5. 作为博客作者，我想将未完成文章标记为草稿，以便在提交到仓库后仍不会意外公开。
6. 作为博客作者，我想将未来发布日期的文章留在非公开状态，以便按计划发布内容。
7. 作为博客作者，我想为文章设置一个受控主分类和多个自由标签，以便建立稳定导航并保留细粒度关联。
8. 作为博客作者，我想使用稳定的文章与聚合页 URL，以便历史链接、搜索结果和 RSS 引用不会失效。
9. 作为博客作者，我想在更改已发布文章 URL 时维护重定向，以便旧链接仍然可用。
10. 作为博客作者，我想按需使用封面图并提供替代文本，以便文章卡片更有辨识度且保持无障碍。
11. 作为博客作者，我想让本地图片经过构建优化，以便页面保持较好的加载性能。
12. 作为读者，我想在首页按时间浏览已发布文章，以便快速发现最新技术笔记。
13. 作为读者，我想阅读中文排版舒适的文章正文，以便长时间阅读技术内容时不感到疲劳。
14. 作为读者，我想在明亮与暗色环境中阅读相同风格的网站，以便适应我的设备和偏好。
15. 作为读者，我想通过分类、标签和归档浏览内容，以便找到相关主题。
16. 作为读者，我想订阅 RSS，以便在自己的阅读器中跟踪新文章。
17. 作为读者，我想在文章页看到发布日期与必要时的更新时间，以便判断内容时效。
18. 作为读者，我想访问“关于我”页面，以便了解作者、博客主题和可用联系入口。
19. 作为读者，我想从博客导航到作者公开的社交或联系渠道，以便在需要时继续交流。
20. 作为读者，我想通过 `blog.loliking.com` 使用 HTTPS 访问网站，以便获得一致且安全的访问体验。
22. 作为维护者，我想在一次生产构建中发现无效内容元数据、路由冲突或发布过滤错误，以便避免错误内容上线。
23. 作为维护者，我想只在一个共享位置定义已发布文章集合，以便首页、分类、标签、归档和 RSS 不会出现不一致。
24. 作为维护者，我想使用 GitHub Actions 自动构建和发布，以便不依赖个人设备完成上线。

## Implementation Decisions

- 网站使用 Astro 静态生成，不引入服务端账户、数据库或内容管理系统。
- 内容由一个 Astro Content Collection 统一管理；文章可以是 Markdown 或 MDX。页面、列表、分类、标签、归档与 RSS 都从同一内容来源读取。
- 文章 frontmatter 必填字段为中文标题、人工摘要、带时区的发布日期、全局唯一的 slug 和主分类；可选字段为更新时间、草稿状态、标签和封面。
- slug 使用仅含小写 ASCII 字母、数字和连字符的 kebab-case，且无首尾斜杠。已发布 slug 默认不可变；变更时由集中维护的重定向表生成静态旧地址跳转。
- 所有文章列表以发布日期倒序排列，同日文章以 slug 升序作为确定性的次级排序。更新时间不得早于发布日期。
- 草稿默认不发布。唯一的发布谓词为“非草稿且发布日期不晚于构建时间”；生产文章页、首页、分类、标签、归档和 RSS 必须共同使用它。开发服务器允许作者预览草稿和未来文章，生产预览与部署则使用发布过滤后的输出。
- 每篇文章只有一个分类。分类以稳定英文 key 与中文展示名称组成受控 taxonomy；内容与 URL 只使用 key。具体首批分类可在实现时补充，不改变该结构。
- 标签可自由填写，但在内容校验时去除首尾空格、进行 Unicode NFC 规范化、将英文转为小写，并在文章内去重。规范化后产生稳定标签 URL；URL 冲突必须使构建失败并要求作者消歧。
- 封面图为可选的图片与替代文本组合。信息性封面必须有有意义的替代文本，装饰性封面使用明确的空替代文本。优先使用与内容相邻的本地图片并走 Astro 图片优化；任何远程图片来源都需要显式信任配置。
- 视觉系统采用暖白、轻微纸张质感、克制的字体层级与充足留白；暗色模式跟随系统并提供手动切换，保持同等阅读层级与对比度。
- 首页提供已发布文章列表；文章页提供正文、日期、可选更新时间、分类、标签与可选封面；另提供分类、标签、归档、RSS 与“关于我”页面。社交与联系入口使用可配置数据，首版允许为空。
- GitHub Actions 构建并部署静态产物到 GitHub Pages。Pages 以 `blog.loliking.com` 作为自定义规范域名；站点配置以该 HTTPS 地址为站点地址，不设置仓库子路径。域名验证、DNS 记录和 HTTPS 强制在部署设置中完成。
- 首版预留统计配置接口但不加载第三方统计脚本。

## Testing Decisions

- 本项目当前没有既有测试模块或测试先例。以一次生产静态构建及其生成页面作为最高且唯一的验证缝，优先测试读者可见结果而不是组件内部实现。
- 内容校验必须在构建时验证必填元数据、slug 格式与唯一性、分类 key、标签规范化冲突、日期顺序、封面替代文本，以及本地/远程图片约束。
- 构建级测试应证明草稿和未来文章不会出现在生产文章路由、首页、分类、标签、归档或 RSS；已发布文章应同时出现在其应有的所有读者入口。
- 构建级测试应证明 URL、重定向、分类页、标签页、归档、RSS、站点地图与规范域名生成正确的公开地址。
- 构建级测试应验证明暗主题切换可用、主要阅读页面具有可访问的结构和足够对比度，并且封面图的替代文本按契约输出。
- 以最少的代表性文章夹具覆盖普通文章、MDX 文章、草稿、未来文章、带更新时间文章、带封面文章、带多个标签文章和需要重定向的文章，避免为每个页面复制同一行为测试。

## Out of Scope

- 评论、用户账户、内容审核和其他动态社区功能。
- 内容管理系统、数据库与服务端写入接口。
- 首版站内搜索、系列专题和启用中的第三方访问统计。
- 首批分类、具体标签、社交账号、联系信息及“关于我”页面最终文案。
- 超出 GitHub Pages 静态托管能力的服务端重定向或个性化功能。

## Further Notes

- 项目尚未初始化 Astro；实现应先建立最小的静态站骨架与唯一构建验证缝，再扩展页面与视觉系统。
- DNS 的具体记录值取决于 GitHub 用户名与域名当前记录。部署前应先在 GitHub 验证域名、设置自定义域名，再按 GitHub Pages 要求配置 DNS，最后启用 HTTPS 强制。
- 未跟踪的 `.DS_Store` 文件不是本规格的一部分，也不应纳入后续提交。
